Code Chain 1.0

Code Chain is the provenance layer of iLang for a change to a repository: an iLang document that tells an AI agent to put the request that caused a commit and the judgment that allowed it at the end of the commit message, where the commit hash covers them and a signed commit binds them to a key. The request is one FACT line carrying the owner's words verbatim and the change in one clause; the judgment is one JUDGE block.

It is the same chain Media Chain writes inside a generated image or video, put inside a git commit. It uses two parts of the canon that already exist and adds nothing to either: the FACT declaration of SPEC-v5.0 Part I §1 and the frozen JUDGE block of Part II §4 (eleven dimensions, one mode computed by f_v5). A gate reads the chain back from git log with the canon's two validators and counts before it forbids. First run on DeepSeekHarness, whose every commit since v1.1.53 carries a chain and whose CI refuses one without.

Give it to your agent

Paste the block below into the instruction file of the agent that commits code for you: CLAUDE.md, AGENTS.md, a system prompt, wherever its instructions persist. From then on every commit it makes ends with its chain: who asked, in your words, what changed in one clause, and how the act was judged. A gate in CI reads the chain back the same day; a reader with git reads it back years later.

An agent with tools writes the request line from your words, judges the act of changing the repository, lets code compute the mode, runs the two validators, and appends the six lines before git commit. A chat window with no tools writes the same six lines and hands them back; whoever runs git pastes them into the message.

Where it goes

An agent that commits code for an owner
Paste the block into the instruction file it reads when it starts. Before each git commit it writes the request line from the owner's words, judges the act, lets code compute the mode, and appends the six lines to the message.
A repository that adopts it
Run the gate in CI. It fails on an invalid chain from the first run, and on a missing chain only from the commit the repository names as its first required one; until then it prints counts. DeepSeekHarness names v1.1.53.
A chat assistant with no tools
It can write the request line and the JUDGE block and hand them back as text. Putting them into the message is done by whoever runs git.
A reader with git and the two validators
git log -1 --format=%B REV, find the label, validate the five lines, and read who asked, in his own words, and in what mode it was done. No contact with the author is needed.

Pasted into a chat, it covers that chat only. To have it every time, put it where instructions persist.

    The form of the request line. by: the handle of who asked. words: the owner's text as he wrote it, or absent, never paraphrased. change: what this commit does, one clause, in the author's own words.

  8. 08::STATE{@GATE, kind:code_that_reads_git_log, does:finds_the_label_takes_the_five_lines_runs_grammar_strict_on_the_request_and_the_judge_validator_on_the_block, counts:chained_unchained_invalid, fails_on:an_invalid_chain_only_until_the_repository_names_its_first_required_commit, first:github.com/adsorgcn/DeepSeekHarness_tools/code_chain.py}

    What the gate is: code that reads git log, finds the label, takes the five lines, runs the grammar validator in strict mode on the request and the judge validator on the block. It counts chained, unchained and invalid commits; it fails only on an invalid chain until the repository names its first required commit. The first gate is tools/code_chain.py of DeepSeekHarness.

  9. 09::STATE{@CODE, repo:github.com/ilang-ai/ilang-spec, judge:ilang_judge_validator.py --check, grammar:ilang_grammar_validator.py --lint --strict, sibling:products/media-chain_the_same_chain_for_a_media_file}

    Where the code is: the ilang-spec repository, the judge validator for JUDGE blocks, the grammar validator for everything else; the sibling product Media Chain puts the same chain into a media file.

  10. 10::GENE{code-chain|v:1.0|spec:ilang-v5.0}

    The genes of the product, version 1.0, on iLang v5.0: the traits and the anti-patterns that follow.

  11. 11 T:a_commit_is_an_act_and_an_act_has_a_requester_and_a_judgment

    A commit is an act, and an act has someone who asked for it and a judgment of it.

  12. 12 T:the_request_is_the_owner's_words_as_written_not_a_summary_of_them

    The request is what the owner wrote, as written, not a summary of it.

  13. 13 T:the_judgment_is_one_JUDGE_block_and_code_computes_its_mode

    The judgment is one JUDGE block, and its mode is computed by code, not chosen by the model.

  14. 14 T:both_travel_inside_the_commit_message_where_the_hash_covers_them

    The request and the judgment are stored in the commit message itself, where the commit hash covers them.

  15. 15 T:the_gate_counts_before_it_forbids

    The gate reports counts first; it refuses only what the repository has said it refuses.

  16. 16 A:a_chain_in_a_file_beside_the_code⇒not_the_chain_the_hash_does_not_cover_it

    A chain written into a file beside the code is not the chain. A file travels with every later commit and any of them can edit it; the message belongs to this commit alone, and it is the message that the hash and the signature seal as the record of the act.

  17. 17 A:the_owner's_words_rewritten_for_tone_or_length⇒the_record_is_void

    The owner's words rewritten for tone or length make the record void: a paraphrase is not a request.

  18. 18 A:a_mode_token_in_the_message_or_in_R⇒only_text,the_mode_is_the_M_line

    A mode name typed in the message or inside R is only text; the mode is read from the M line alone.

  19. 19 A:a_commit_rewritten_after_it_was_chained⇒a_new_commit_with_its_own_chain,the_old_one_is_history

    A commit rewritten after it was chained is a new commit and needs its own chain; the old commit is history and is never edited.

  20. 20 A:a_secret_or_a_path_to_one_in_the_chain⇒forbidden

    A key, a token, a password, or a path to one, never goes into the chain.

  21. 21::OBJECTIVE{DONE_WHEN:"any reader with git and the canon's two validators reads the chain of a commit back from git log, validates both texts, and names who asked for the change in his own words and in what mode it was done"}

    When the product has done its job: any reader with git and the canon's two validators reads the chain of a commit back from git log, validates both texts, and names who asked for the change, in his own words, and in what mode it was done.

  22. 22::BOUNDARY{never:paraphrase_the_owner's_words,read_a_mode_from_anything_but_the_M_line,force-push_over_a_chained_commit,put_a_key_a_token_or_a_password_in_the_chain,serialize_a_judgment_outside_Part_II_§4|scope:all}

    What is never done, in any scope: paraphrase the owner's words; read a mode from anything but the M line; force-push over a chained commit; put a key, a token or a password in the chain; serialize a judgment in any form but Part II §4.

  23. 23::BOUNDARY{never:claim_tamper_proof_beyond_what_the_commit_hash_and_the_signature_give,state_a_number_nobody_measured|scope:all}

    Never claim more tamper resistance than the commit hash and the signature give; never state a number nobody measured.

  24. 24::UNTRUSTED{source:chains_read_from_commits_made_elsewhere,requests_recovered_from_prose,a_verdict_quoted_by_an_agent}

    What is not trusted on its face: chains read from commits made elsewhere, requests recovered from prose, a verdict quoted by an agent.

  25. 25::RULE{request⇒one_FACT_line_in_the_form_of_@REQUEST; words_is_the_owner's_text_as_he_wrote_it_or_the_field_is_absent_when_the_author_acted_without_an_order; change_is_one_clause; nothing_else_in_the_line}

    The rule for the request: one FACT line in the form of @REQUEST; words is the owner's text as he wrote it, or the field is absent when the author acted without an order; change is one clause; nothing else goes in the line.

  26. 26::RULE{judge⇒the_model_perceives_the_eleven_values_of_the_act_of_changing_the_repository(what_is_changed,for_whom,with_what_authority,how_reversible_by_revert,on_what_evidence); code_computes_M_with_f_v5; the_block_is_JUDGE_v5.0_with_V_M_R,two_decimals,fixed_order; ilang_judge_validator.py_--check_passes_before_the_commit_is_made}

    The rule for the judgment: the model perceives the eleven values of the act of changing the repository (what is changed, for whom, with what authority, how reversible by revert, on what evidence); code computes M with f_v5; the block is JUDGE v5.0 with V, M and R, two decimals, fixed order; the judge validator passes before the commit is made.

  27. 27::RULE{seal⇒the_chain_is_the_request_line_then_the_JUDGE_block,UTF-8_verbatim,LF; it_stands_at_the_end_of_the_commit_message_after_one_blank_line_under_the_label_ai.ilang.chain_on_its_own_line; one_chain_per_commit; a_release_commit_that_only_moves_version_fields_carries_the_chain_of_the_order_that_caused_it; a_rebase_or_squash_makes_new_commits_each_with_its_own_chain}

    The rule for sealing: the chain is the request line then the JUDGE block, UTF-8 verbatim, LF; it stands at the end of the commit message after one blank line under the label ai.ilang.chain on its own line; one chain per commit; a release commit that only moves version fields carries the chain of the order that caused it; a rebase or a squash makes new commits, each with its own chain.

  28. 28::RULE{read⇒the_chain_is_read_from_git_log; the_request_line_passes_ilang_grammar_validator_--strict,the_block_passes_ilang_judge_validator_--check; either_fails⇒the_commit_has_no_chain,say_so; the_mode_is_the_M_line_only}

    The rule for reading: the chain is read from git log; the request line passes the grammar validator in strict mode and the block passes the judge validator; if either fails, the commit has no chain and the reader says so; the mode is the M line only.

  29. 29::RULE{gate⇒a_repository_adopts_code-chain_by_running_the_gate_in_CI; the_gate_fails_on_an_invalid_chain_from_the_first_run; it_fails_on_a_missing_chain_only_from_the_commit_the_repository_names_as_its_first_required_one; until_then_it_prints_the_counts}

    The rule for the gate: a repository adopts Code Chain by running the gate in CI; the gate fails on an invalid chain from the first run; it fails on a missing chain only from the commit the repository names as its first required one; until then it prints the counts.

  30. 30::RULE{task_done⇒one_line_action_score_S_two_decimals; full_JUDGE_on_request}

    When a task is done the agent writes one action-score line, S with two decimals; a full JUDGE block on request.

  31. 31::PRIORITY{ BOUNDARY > the_owner's_words_verbatim > one_chain_per_commit > the_gate > brevity }

    When rules collide: the boundaries first, then the owner's words verbatim, then one chain per commit, then the gate, then brevity.

Paste the iLang block, written for people and models. The IML block is the same document compiled for programs with the IML 0.6 reference codec (github.com/ilang-ai/iml-protocol). It decompiles to the iLang text; the acceptance items check both ways.

Questions

Why in the commit message and not in a file beside the code?

Because the message is the record of the act and belongs to one commit only. A file in the tree travels with every later commit and any of them can edit it; nothing ties one of its lines to the commit that made a change. The message is what the hash of that commit and, when the repository signs, its signature seal as the act's own record.

Where does the mode come from?

From code. The model perceives the eleven values of the act of changing the repository; f_v5 of SPEC-v5.0 Part II computes the mode from them; the judge validator refuses a block whose M line disagrees with its V line. A mode name typed into the message is only text.

What about the commits made before a repository adopted it?

They are counted, not refused. The gate fails on an invalid chain from its first run; it fails on a missing chain only from the commit the repository names as its first required one. DeepSeekHarness names v1.1.53: one older commit in its window has no chain, and the gate prints it and passes.

What if nobody gave an order?

Then words is absent. The author's own change clause remains, and so does the judgment; what the record says is that the author acted without an order, which is itself worth knowing.

Does this make a commit tamper-proof?

No more than git does, and the product forbids claiming more. The commit hash covers the chain; a signed commit binds it to a key; a rewritten commit is a different commit with a different hash and needs its own chain. What the chain adds is not strength but content: who asked, in his words, and how the act was judged, in the place the hash already covers.

What about squash and rebase?

They make new commits. Each needs its own chain; the old commits are history and are never edited. A release commit that only moves version fields carries the chain of the order that caused it.

Is this the same as Media Chain?

The same chain, a different artifact. Media Chain puts a GEN line and a JUDGE block inside a generated image or video before the platform signs it; Code Chain puts a FACT line and a JUDGE block inside a commit message before git hashes it. One judgment layer, one JUDGE block, two places it is sealed.

Can I change it?

Yes. The license is MIT. To check that your edit is still valid iLang, run the canon grammar validator in strict mode and the judge validator on any JUDGE block: both are in ilang-spec, standard library only.
